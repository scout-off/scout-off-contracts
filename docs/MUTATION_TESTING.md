# Mutation Testing

This document describes the mutation testing setup for the scout-off-contracts workspace, including the baseline results and procedures for running and maintaining mutation tests.

## Overview

Mutation testing uses `cargo-mutants` to introduce small changes (mutations) to the codebase and verifies whether the existing test suite catches them. Surviving mutants indicate gaps in test coverage that could allow bugs to reach production.

## Scope

Mutation testing is scoped to the highest-risk code:

- **`contracts/scout_access/src/lib.rs`** - Payment and escrow functions:
  - `subscribe`
  - `pay_to_contact`
  - `batch_contact_players`
  - `log_trial_offer`
  - `confirm_trial_offer`
  - `expire_trial_offers`
  - `withdraw_fees`
  - `refund_subscription`

- **`contracts/shared-types/src/lib.rs`** - Safe math helpers and validation:
  - `safe_math` module (safe arithmetic for u32, u64, i128)
  - `validate_cid` (IPFS CID validation)
  - Wiring helpers (cross-contract link verification)

## Exclusions

The following are excluded from mutation testing:

- **Generated code**: Event helpers in `events.rs` (generated by `#[contractevent]`)
- **Cross-contract client stubs**: `progress_contract` and `registration_contract` modules (generated by `#[contractclient]`)
- **Test-only code**: Functions in `testutils` modules

## Configuration

The `mutants.toml` file at the repository root configures the mutation testing scope:

```toml
[package]
workspace_members = [
    "scoutchain-scout-access",
    "scoutchain-shared-types",
]

[exclude]
files = [
    "contracts/scout_access/src/events.rs",
]

patterns = [
    "progress_contract",
    "registration_contract",
]
```

## Running Locally

### Prerequisites

Install `cargo-mutants`:

```bash
cargo install cargo-mutants
```

Ensure the workspace tests pass first:

```bash
cargo test --workspace --locked
```

### Basic Run

Run mutation testing on the configured scope:

```bash
cargo mutants --config mutants.toml
```

### Sharded Run (Recommended)

For faster results on multi-core machines, use sharding:

```bash
# Run shard 1 of 4
cargo mutants --config mutants.toml --shard 1/4

# Run shard 2 of 4
cargo mutants --config mutants.toml --shard 2/4

# Run shard 3 of 4
cargo mutants --config mutants.toml --shard 3/4

# Run shard 4 of 4
cargo mutants --config mutants.toml --shard 4/4
```

### In-Place Mode

For CI or when you want to keep mutated source for inspection:

```bash
cargo mutants --config mutants.toml --in-place
```

## CI Integration

A scheduled GitHub Actions workflow runs mutation testing weekly and uploads the report as an artifact. The workflow:

1. Runs on a weekly schedule (cron: `0 0 * * 0`)
2. Can be triggered manually via `workflow_dispatch`
3. Uses sharding across a matrix for parallel execution
4. Uploads `mutants.out/` as an artifact
5. Fails if the missed count exceeds the documented baseline

See `.github/workflows/mutation-testing.yml` for the full workflow definition.

## Maintenance Guidelines

### When to Update the Baseline

Update the documented baseline in this file when:

1. **New tests are added** that kill previously missed mutants
2. **Code is refactored** in a way that changes the mutation landscape
3. **Intentional behavior changes** make previously meaningful mutants equivalent

### Process for Updating Baseline

1. Run mutation testing locally with the latest code
2. Review each missed mutant:
   - If it represents a real gap, add a test to kill it
   - If it is equivalent, document the justification
3. Update the baseline counts in this document
4. Update the CI workflow's baseline threshold if needed
5. Submit a PR with the changes

### Regression Detection

The CI workflow will fail if the number of missed mutants increases above the baseline. This indicates:

- A test was removed or weakened
- New code was added without adequate test coverage
- A refactoring introduced untested edge cases

Investigate and fix the regression before merging changes that increase the missed count.
